# What is unfinished, and where we would go next
Date: 2026-11-01
Summary: An honest list of the gaps behind the flying-fish demonstration, and the directions we think are worth the next effort.

A demonstration can look more finished than it is. This post lists the places where it is not.

## Gaps in the science

- **The fish is a candidate, not a viable organism.** Its geometry, equations and simulations are inspectable. Nothing establishes that it could develop, or that a set of edits would produce it.
- **Cross-scale bridges are mostly unsupported.** The coupling layer refuses most of the connections one would like, because no registered calibration exists. Producing calibrations is an experimental problem, not a software one.
- **Sequence to function is thin.** Genomes for zebrafish and flying fish exist, and the gene, enhancer and protein work is a ledger of sourced leads. Linking each design change to specific DNA changes is under way and not complete.
- **Generative modelling is a pilot.** The diffusion work learns an abstract pattern model. A model that learns control knobs for organism design from forward simulation is a research direction, not a result.

## Gaps in the platform

- **Collaboration is designed more than exercised.** The record layer separates review from identity so independent operators could review elsewhere. This deployment is one node, and we do not claim a federated network.
- **Open goals.** The self-validation loop, additional simulators for computationally designed organisms and a complete multiscale browser remain unchecked in our own goal list.
- **Nanopublication verification was not run** against the network. Imported records keep their provenance and upstream status.

## Where we would go next

1. **Design experiments that pay off across scales.** Choose the measurement that most reduces uncertainty at an interface, then feed the result back as a registered calibration.
2. **Grow the Lean base.** More laws with explicit scope, and conflict certificates for design constraints, so solvers and generators work from checked statements.
3. **Use the frontier for other designs.** The same machinery applies to scoped problems that cross only a few scales, for example a neural circuit or a metabolic switch.
4. **Measure the swarm.** Compare shared and isolated agents on the same open question and publish the result either way.
5. **Make uncertainty a design output.** A per-region map of how well supported each part of a design is, by theorem, simulation and evidence.

If you work on one of these and want to contribute a source, a disputed parameter, a model adapter or an independent check, the [documentation](#/about/docs) describes the record contracts and the MCP interface.
